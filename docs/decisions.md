# Decision log

Decisions made while building v1, newest last. Each entry: what was decided, why, and where it applies.

## 2026-10-25

1. **Sections, top to bottom: Human, Claude, Backlog, Done.** What needs the person sits on top and never scrolls off. Done is collapsed by default and shows the 10 most recent cards.
2. **Rows, not columns.** The side pane is narrow; stacked sections fit. Each section shows at most 5 cards and scrolls on its own with the wheel (`ui.scroll` hook + pointer hit-testing). Clickable `↑/↓ N more` rows are the reliable fallback where hit-testing is imprecise (desktop).
3. **Buttons first, drag later.** Drag needs a `Client` element, which exists only on the terminal and desktop surfaces. v1 ships button moves everywhere (#2); drag is #8 and leaves VS Code and mobile on buttons.
4. **GitHub mapping onto the existing board, no board restructuring.** Backlog = Status Backlog or Ready; Claude = Status In progress (with or without the `ai` label); Human = Status In review or label `human`; Done = Status Done or closed. A backlog issue labeled `human` stays in Backlog: the column is who holds the ball now.
5. **Move to Human sets Status In review, no label change. Move to Claude adds `ai` and removes `human` if present.** Least label churn while keeping the ownership label right for the person's own `gh issue list --label ai` workflow.
6. **Approve = Done + close the issue, then verify it is closed.** Matches "Done means closed"; `gh issue close` can fail silently, so the state is re-read.
7. **Optimistic sync.** The card moves at once; ⟳ pulses (a cell can't rotate), ✓ bright for 1 s then dim for 1 s then gone, ✕ with Retry. After the first try plus 3 retries fail, the card snaps back and a toast gives the reason. Rapid moves of one card collapse into one request for the final target (300 ms debounce, plus queueing while a request is in flight).
8. **Prompts to Claude fire only after the move is confirmed.** Dropping Backlog→Claude submits "Work on kanban card #N"; Send back submits "Resume kanban card #N". Claude's own `kanban_move` calls never submit prompts (no loops).
9. **Handoff is enforced, not suggested.** `kanban_move` to Human is refused unless the newest handoff comes after the newest feedback and has non-empty **Check** and **Need from you**. A Write/Edit guard applies the same rule to direct `.kanban/*.md` edits; the guard fails open so it can never block unrelated editing.
10. **One backend per project, no sync between them.** Two sources of truth means sync bugs. Choice is a `backend` setting (`auto` / `github` / `local`, #10); `github` never silently falls back.
11. **Polling every 45 s while the pane is open**, plus a refresh button. GitHub has no push to a local process; 45 s is well inside API rate limits for one person.
12. **Cache per working directory in `$.store`** so the pane opens instantly; remote data wins on refresh except for cards with a pending or failed move.
13. **No mutating `gh` commands during development.** All write paths are tested against fakes; only read-only `gh` calls touch real repos.
14. **Repo and tracking.** Public repo `TeeratP/claude-kanban`, board #7, code `KANB`. Epic #1 with sub-issues #2–#10. Foundation (#2) lands on `main` first; the rest branch from `changes-20261025` in `.worktrees/<branch>` and run in parallel.
15. **Live dev copy.** The engine hot-reloads from the session's `dev-mods/.../kanban/` folder; that folder is synced from the repo's `main` (rsync) after each merge rather than symlinked, because symlink handling in the watcher is not something worth depending on.
16. **Backends are plain functions, not objects.** The validator rejects passing `$` to a method call, so `backend.ts` dispatches on `info.kind` to top-level functions (`loadCards`, `moveRemote`, …). (#2)
17. **Atoms live only in `atoms.ts` behind accessors.** The validator only accepts `read`/`update` in the atom's own file. (#2)
18. **`tsconfig.json` drops `claude-code-mcp` types.** On TypeScript 5.6 the 434 KB MCP typings hit TS2589 on the first `tool.call` matcher; the mod needs no other server's tool types. (#2)
19. **Phase-1 `moveCard` awaits the backend; #4 replaces it with the debounced optimistic machine.** Kept phase 1 simple and testable. (#2)
20. **Parallel wave split by file ownership.** `handoff.ts`: #6 owns `formatHandoff`/`isHandoffValid`, #7 owns `formatFeedback`. `sync.ts`: #4 owns the state machine and prompt firing; #7 only passes `onConfirm`. Diff: #7 adds the `readDiff` dispatcher, #3 fills the GitHub branch. `detectBackend` gets a `mode` parameter now (#3) so the `backend` setting (#10) is a small follow-up.
21. **Merge order into `changes-20261025`:** #3 → #4 → #5 → #6 → #7 → #8 → #9, then #10. Backend and sync first because the most files depend on them; drag last because it rewrites board rendering.
22. **Merge as branches finish, not strictly in the planned order.** Docs (#9) and polling (#5) finished first and touch few shared files; waiting would idle the integration branch. Conflicts are resolved at each merge with full gates.
23. **Cache never counts as "loaded".** A cache-painted board keeps `fetchedAt: 0`, so tools wait for a real load and never act on stale columns. (#5)
24. **"Newly in Human" toasts come only from loads, plus one from Claude's `kanban_move`.** The person's own moves are already on the board when a refresh compares, so they never toast; refused or snapped-back moves never announce. Toast text is neutral ("Waiting on you: #N title") because a card can arrive from several sources. (#5)
25. **Backend setting must invalidate the cache.** The cache restores `backend`; #10 drops it when the setting changes. (#5 → #10)
26. **Handoff check is ordered by section position, dates are day-granular; placeholders (`…`, `...`, `n/a`, empty) don't count.** (#6)
27. **No duplicate announcements.** `kanban_move` does not toast itself; #5's `announceHandoff` gives exactly one toast + notification. (#6, #5)
28. **Write/Edit guard blocks only a transition into Human**, so Claude can still edit the spec of a card the person moved to Human. It is a guard rail, not a security boundary (Bash/sed edits are not covered). (#6)
29. **`kanban_create` cannot create into Human** — that would bypass the handoff rule. Local only; on GitHub it points to the /issue skill. (#6)
30. **Unknown frontmatter keys are preserved**, and indented lines are values, not keys, so nested `id:`/`status:` can't override a card's own. (#6)
31. **Card creation is serialized** so two parallel creates can't pick the same number. (#6)
32. **`gh project item-list` output is trimmed with `--jq`** to the fields used, to stay under the engine's 4 MiB stdout cap on big boards. (#3)
33. **Repo is parsed only from a `Repo:`-style label with a backticked `owner/name`.** Stricter than the plan, because a move writes to that repo; a wrong match must not happen. (#3)
34. **CLAUDE.md ids win; `gh project field-list`/`view` only fill gaps. Any detection failure → local with a debug log** (under `auto`). (#3)
35. **A partially-applied GitHub move is not rolled back remotely.** The card snaps back locally and the next refresh shows the true remote state; retry reruns the idempotent sequence. (#3)
36. **Mobile is detected by `e.surface`, not by element presence.** The mobile element table still contains `Input` at runtime even though the types omit it. (#7)
37. **The feedback draft is cleared when another card opens**, so feedback can't be sent to the wrong card. (#7)
38. **Send back records feedback before moving.** If the move is refused, the card snaps back to Human but the feedback stays recorded. (#7)
39. **Commit trailers from implementers name the model that wrote the code** (harness attribution), so branch commits say Sonnet and orchestrator commits say Opus. Left as is. (all)
40. **Integration moved to its own worktree** (`.worktrees/integration`) once merges needed conflict work, so the repo root stays on `main` (== `origin/main`). A Sonnet integrator resolves conflicts; the orchestrator reviews and logs.
41. **`moveCard` no longer reports success synchronously; `kanban_move` answers "Moved #N to X (syncing)."** The Human announcement moved to the confirm path, so it fires only after the backend confirms. (#4, integration)
42. **No refresh after a confirmed move; the backend patch is applied only if the card still shows that move's column.** A stale patch never overwrites a newer optimistic move. A card leaving Human drops its `tag` in the patch itself. (#4, #3, integration)
43. **After a snap-back the card lands at the bottom of its old section, then a refresh restores its real position.** Avoids storing a `fromOrder`. (#4)
44. **A move made while one is in flight is queued; only the last target is sent.** If the in-flight call fails after a newer target was asked for, the newer one is sent with attempts reset. (#4)
45. **Drag targets are section headers only; drag Backlog→Claude submits the work prompt like the move buttons.** (#8, integration)
46. **Surface is detected by `e.surface`, not by element presence**, for the Client too: `$.ui.resolve(e)` returns a `Client` on every surface, a no-op fragment on vscode/mobile. (#8)
47. **The toolbar stays outside the Client** so layout row index = tree row and wheel hit-testing is unchanged. The Client has no wheel event, so the pane's `ui.scroll` still drives per-section scroll. Unverified in a live renderer. (#8)
48. **Keyboard access to Client board rows is a follow-up (#11, p1)**, not shipped in v1. The detail view's Buttons stay keyboard-reachable. Also opened #12 (status line at session start), #13 (paging past 500 GitHub items), #14 (escape section markers in handoff text).
49. **`announce` rides on the sync entry** like `onConfirm`: it survives reloads and retries, and is dropped if the person retargets the move. (integration)
50. **One rule for "Backlog→Claude by the person sends the work prompt": `moveOptions(from, to)` in `sync.ts`**, used by both the move buttons and drag drops. (integration)
51. **Tests assert behaviour on both Button rows and Client rows through shared helpers** (`tests/board-ui.ts`), so no assertion passes vacuously on a surface that draws rows differently. (integration)
52. **The backend setting's mode is stored on the board.** The engine keeps the board atom across the reload that a setting change causes, so `session.start` compares modes and resets the board when it differs; the same mode keeps the board across a hot reload. (#10)
53. **`github` mode surfaces the failing check with a fix hint and re-checks on every refresh**, so it recovers by itself once `gh` is fixed. `auto` keeps logging quietly and falling back to local. (#10)
54. **A cache saved under another mode is ignored, not deleted**, and overwritten by the next successful load. (#10)
55. **Toolbar label is `GitHub (auto)` / `GitHub` / `Local (auto)` / `Local`, empty until the backend is known under `auto`**, so it never claims Local while GitHub may be about to load. (#10)
56. **At session start with the pane closed, only the status line comes from the cache**; cached cards are not written to the board, so no stuck `isLoading` and no flood of "newly in Human" toasts on the next load. The cache only speaks for an unloaded board under the same mode. (#12)
57. **Section markers in handoff fields and feedback are escaped, not stripped.** `## Handoff (` / `## Feedback (` lines get a leading `\` (renders as literal text; indenting would still render a heading or a code block); field markers get an escaped colon (`**Check\:**`, still bold, no stray characters). Every line of multi-line values is escaped; the escape is idempotent. (#14)
58. **A literal `## Handoff (date)` line in a local card spec ends the spec and starts a section**, the same as hand-writing a handoff, which is allowed. GitHub issue bodies are never parsed for sections. Claude bypassing the tools (posting a raw `gh issue comment` or a Bash edit) is out of scope for the guard: it is a guard rail, not a security boundary (see 28). (#14)
59. **GitHub item-list is paged by gh itself; the ceiling is 3000 items with a 180 s timeout**, and both lists are trimmed with `--jq` (3000 worst-case items ≈ 2.2 MB, about half the 4 MiB cap). (#13) Superseded for loading by #15's single GraphQL query once it lands.
60. **Keyboard access in the Client needs one click first.** The engine gives a `Client` keys only after a click (no Tab or plugin focus), so v1 offers ↑↓/j/k, Enter and `m` + section key after a click; the cursor appears only on the first key, so mouse users see no change. Keyboard-only entry would need a hooks-side cursor with Button hotkeys — left as a known limitation. (#11)
61. **The toolbar key hint shows whole or not at all.** With the longer `Local (auto)` label (#10) it no longer fits a 44-column pane; a cut hint is noise. (integration of #10 + #11)
62. **Review findings and a rate-limit problem are fixed before `main`**: #15 (one cheap GraphQL query, rate-limit backoff, `Human` label case, ensure `ai` label, only the signed-in user's handoff comments count) and #16 (confirmed moves undone by in-flight loads, wheel at edges, ticker race, escaped `kanban_create` spec, README).
63. **A move confirmed while a load is in flight is protected by a per-load "confirmed" set, not by the sync entry.** `ok` entries expire after 2 s, and paged GitHub loads can be slower, so relying on the entry would still undo the move. (#16)
64. **The wheel passes to the engine whenever a section's window doesn't move**, so rows below a short pane stay reachable. (#16)
65. **Next feature wave (#17–#22), requested 2026-10-26:** agent badge + live activity + time/tokens (#17), keyboard review flow (#18), run Check from the card (#19), Claude WIP limit + queue (#20), `kanban_ask` blocking questions (#21), drop anywhere + reorder (#22). 66. **Quick add on GitHub creates the issue with the `triage` label in Backlog**, matching the user's grooming convention (title prefix and type/priority/ownership labels are applied when groomed). `kanban_create` gains the same GitHub path instead of refusing. (#23)
67. **Follow-ups from the chat are suggestions, not cards.** Claude calls `kanban_suggest`; the person presses Add or Dismiss. Nothing is created without a press. (#24)
68. **Filtering is display-only** and resets per-section scroll; drag, keyboard and moves act on visible rows. (#25)
69. **Ordering of the later wave:** #23 → #24 after #15 (GitHub create path); #25 after #17 and #22 (shared row and layout code). Item 16 of the UX list (reorder within a section) is part of #22.
70. **GitHub loads use one paged GraphQL query on the project node: cost 2 points per refresh (measured on board #7), down from about 104.** At 45 s polling that is about 160 points an hour instead of about 8000. Paging is capped at 30 pages (3000 items), logged to debug. (#15)
71. **Rate-limit backoff:** polling pauses when the budget is low (≤ 100 points left) or any gh error matches `/rate limit/i`, until `resetAt` (or 5 min for secondary limits). The toolbar shows `limit low · paused Nm` / `limit hit · paused Nm`; a manual refresh still runs, with a toast. (#15)
72. **Label edit runs before the Status edit**, so a failure leaves nothing half-done; the `ai` label is created once if missing (never overwriting an existing one, case-insensitive); `human` is matched case-insensitively and removed under its real spelling. (#15)
73. **Only the signed-in user's handoff and feedback comments count.** Others' are shown as `from @login, not counted`. If the viewer can't be resolved, moves to Human are denied rather than trusting unknown authors. (#15)
74. **The GitHub board query costs 3 points a page, up from 2, to load the newest comments** so a question card keeps its `?` tag after a restart (about 240 points an hour at 45 s polling, still far under 5000). Accepted over "tag only for questions asked this session". (#21)
75. **A question counts as a handoff until it's answered.** Cards carry the question's one-line gist for toasts ("Claude asks: … (#N)"), dropped when the card leaves Human. A refused move after an ask keeps the saved Question section. (#21)
76. **Branches that predate the shared-file changes rebase themselves.** When a branch conflicts in several shared files, it goes back to its own agent, which knows the change, to merge the integration branch and fix it. The orchestrator doesn't resolve semantic conflicts blind. (#20)
77. **Agent activity sits on a second dim row under a Claude card**, shown only once the card has a recorded round (never for a queued card that hasn't started). Name = the subagent's name or type, colour = FNV-1a hash into a fixed theme palette that avoids the sync colours. Time is main-turn wall time; tokens = input + cache writes + output from `turn.step`, cache reads shown apart. Totals persist per card in `$.store`. (#17)
78. **Attribution:** a turn belongs to the card whose work/resume/answer prompt started it (`noteCardPrompt` inside `submitPrompt`, the one place prompts are sent), else to the card a main-loop `kanban_*` tool touched while it's in Claude. Subagents inherit the spawner's card. (#17, integration)
79. **Review keys:** `a` approve, `s` send back/answer, `p` park, `f` write, `n`/`k` next/previous Human card, `b` back. Esc belongs to the engine and can't be used. After a decision the next Human card opens, and decisions on it are ignored for 600 ms so a double press can't approve two cards. (#18)
80. **Run check:** commands come from the newest counted handoff's Check field (code spans that look like commands, fenced sh/bash blocks), run only on the person's press via `sh -c` with a 5-minute timeout and no Stop button (`$.process.run` can't abort). Local cards record a `## Check run` section; GitHub only on "Attach to card". Other authors' sections never supply a command. A recorded check run doesn't close an open question. (#19, integration)
81. **Claude WIP limit:** `claudeLimit` setting, default 1, `0` = unlimited. Only moves that carry a prompt (person's Backlog→Claude, Send back, Answer) are held; Claude's own moves use slots but are never queued. Queue order = Claude section order, so queued cards can be reordered; saved per cwd + mode. (#20, integration)
82. **Drop anywhere:** a drop on a header or empty row puts the card first; on a card, before it, or after it when the pointer was moving down (or in the lower half where sub-cell position is known). A drop on a card's activity row means after that card. Done keeps no manual order. Order is saved as sparse local `order` values or GitHub's item position (`updateProjectV2ItemPosition`); a reorder never sends a prompt, never leaves the queue, never ends an activity round. (#22, #26, integration)

The optimistic `#0` card is inert: not openable, movable, droppable-onto, listed by tools, or cached. A GitHub create that fails after the issue exists names the issue in the toast; nothing is rolled back remotely. (#23, integration)
84. **Suggestions** live in a strip outside the Client; the wheel's hit-test subtracts its height. Suggestions persist per cwd; Add removes the row and restores it if the backend refuses; `why` is appended to the card text. A short `prompt.compose` section asks Claude to suggest follow-ups rather than create cards. Dismissed suggestions are forgotten (#27 tracks remembering them). (#24)

Words AND together on titles; `#N`, `[PRJ-AREA]`/`area:`, `@section` are alternatives within their kind; `label:` / `-label:` exact, case-insensitive. Headers show `shown/total`; collapsed sections with matches open without changing the stored flags. Never persisted. (#25)

## 2026-10-26 (hotfix)

92. **Board config is read from `CLAUDE.md`, `.claude/CLAUDE.md` and `AGENTS.md`, following `@path` imports one level deep** (project-relative only, each file once, capped). Projects like punn keep their config in `AGENTS.md` behind a `CLAUDE.md` that is just `@AGENTS.md`. (#32)
93. **Project number accepts `projects/N` URLs, `Project[ board]: #N`, `project number N`, `project **N**`, `project N`, and `#N` near "project"/"board"**, tried in that order; the repo rule stays strict because moves write to that repo. (#32)
94. **When `auto` sees board config it can't parse, it says so**: toolbar `Local (auto) · board config not understood`, plus hint rows on an empty board. Only a saved GitHub backend is reused from the cache, so a project that fell back to local once re-detects next session. (#32)
95. **Zero-config detection:** with no board config, the mod reads `git remote get-url origin`, then checks `gh --version` and `gh auth status`, then asks GitHub (1 point) for open Projects linked to the repo, counting each board's items from this repo. No linked board → scan the viewer's and owner's projects for this repo's items (1 point). One board → used; several → most items; a tie → a picker in the pane, nothing loads until you pick. The result is cached per cwd with the origin URL, so later sessions make no `gh` calls; it re-detects when the origin changes or the board is gone. Explicit CLAUDE.md/AGENTS.md config still wins. (#33)
96. **Boards without an "In review" status still work**: moving to Human adds the `human` label and keeps Status In progress, with a one-time toast. Todo/To Do, Doing, Review and Closed are accepted as status names. (#33)
97. **Plugin version is bumped on every release to `main`** (0.2.0 for #32, 0.3.0 for #33). A marketplace install only updates when the version changes. (orchestrator)
98. **Toolbar is two rows:** a dim status row (backend · board · age; press to change a detected board) and an action row `r: Refresh   n: New   f: Find` that reads as keyboard hints. The engine draws a hotkeyed plain Button as `key: label`, which is why symbol labels (`↻n: +f: 🔍`) looked broken. On narrow panes the query is cut first, then spacing, then Refresh, then New; Find, ✕ and retry always stay. (#34)

## 2026-10-26 (groups and polish)

Spec: `docs/design-groups-polish.md`.

99. **Two groups replace four folds: Active (Backlog, Human, Claude) and Inactive (Done, Cancelled, Suspended).** Requested by the user. One group is open at a time, and pressing the open one folds both. Section folds are gone. (#35)
100. **Active is Backlog, Human, Claude top to bottom, the order the user listed.** The design pass proposed keeping Human on top; the orchestrator overrode it to follow the request literally. With equal fixed heights every section of the open group is always visible, so Human can no longer scroll off, which removes the reason for keeping it first. One constant (`GROUPS`) flips it. (#35)
101. **Inactive is Done, Cancelled, Suspended, the order the user listed** (the design pass proposed Suspended before Cancelled; overridden for the same reason as 100). (#35)
102. **The "ai" section stays labelled Claude.** It is the brand, the prompts, the tool value and the README word; "AI" would be a second name for one thing. (#35)
103. **Equal height:** each section of the open group gets `B = max(2, floor(avail / 3))` body rows. It is filled with cards, `↑`/`↓ N more`, the empty-state line and blank filler. The 0–2 leftover rows go below everything, never to one section. There is no maximum: the height follows the pane, never the cards, so nothing jumps when a card moves. The rows the picker, filter and quick add take come off first. A pane too short for 2 rows each scrolls as a whole. (#35)
104. **The ui atom's shape goes to `ui-4` with `openGroup: 'active'` as the default; no other shape changes.** The ui atom is never stored, so the engine's reset on a shape change is the whole migration. Other atoms and store values only gain union members and optional fields. (#35)
105. **Section headers carry a dim rule to the right edge** (`Human 2 ────`). Equal-height blocks with blank filler need a visible boundary. A rule costs no row. (#35, #36)
106. **Claude's header says `limit 1 · 2 queued`, and `limit 1 · 1 over` in warning when Claude moved more in than the limit**, replacing `2/1`, which read as a fraction. (#35, #36)
107. **Color semantics:** Human = `permission` (the engine's "needs you" color), Claude = `claude`, Backlog plain, the inactive group dim. A folded Active group still shows a non-zero Human count in `permission`. (#36)
108. **Folded groups take drops through chips, not by springing open.** While a card is dragged, a folded group's header shows its sections as chips and the pointer's column picks one. Springing a group open would fold the other and pull the dragged row from under the pointer. Keyboard `m` reaches folded sections through the group row's move keys (`1`–`6`, `h c b d s x`). (#35)
109. **A person's move into Claude from Backlog, Suspended, Cancelled or Done sends the work prompt**; from Human it stays Send back. Taking a card up again is starting work. (#35)
110. **Suspending and cancelling are the person's calls.** `kanban_move` keeps `human | claude | backlog | done`, and it refuses to move a card out of Suspended or Cancelled. Claude asks with `kanban_ask`. A card Claude is still working on keeps its turn running (the mod can't interrupt it); the person gets a toast saying how to stop it. Its WIP slot is freed and the queue moves on once the move is confirmed, as for any card leaving Claude. (#35)
111. **One glyph set, text-presentation only, one cell each** (`▸▾ ⟳✓✕ ● ↑↓ ─ › … · ? ⏎⇧`); no emoji. Emoji draw two cells wide in some terminals and break the one-row guarantee. (#36)
112. **One title column for the whole board.** The number is right-aligned to the widest `#N` on the board. The sync mark takes room only while shown. `?` replaces `#` on a question card. The `rev`/`hum` tags leave the row (both mean "your turn", which the section says) and stay in the detail meta and `kanban_list`. (#36)
113. **The main session's agent dot is always `claude`; subagents hash into the palette without `claude` and `permission`**, so a dot never reads as a section color. (#36)
114. **Relative times tick:** a 30 s ticker runs while the pane is open, so `updated 2m ago` and card ages are never a poll behind. One redraw per 30 s. (#36)
115. **The pane title shows the Human count (`Kanban · 2`) only if re-opening an open pane is proven not to move or focus it.** It is a tab label seen only with several panes, so it is not worth any risk. (#36)
116. **GitHub: Cancelled = closed as not planned, read from `stateReason`; Suspended = a Status option named like suspended/on hold/paused/icebox, else the `suspended` label with Status Backlog.** A board option named like cancelled/won't do/not planned is used when present, but the issue is still closed as not planned, so the close reason stays the source of truth. The Status options come from the first page of the board query, so no extra `gh` call is needed and an option added later is picked up. No options are added to the person's board (decision 4). Without the options, the GitHub board page shows cancelled cards in Done and suspended ones in Backlog with the label. (#35)
117. **Done ↔ Cancelled reopens the issue before closing it again with the other reason**, and the verify reads `state` and `stateReason`. `gh issue close` on a closed issue changes nothing and exits 0. (#35)
